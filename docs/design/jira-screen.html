Herdr Jira

A screen on the icon rail, beside Workspace and Pulse, that shows my Jira work: what is assigned to me, what is stuck, how my board is moving. Each ticket is joined to its GitHub PRs and its Herdr space through the issue key (HDE-314), so one click takes me from a ticket to the terminal where I'm working on it.

Pulse answers "where do my PRs stand?". Jira answers "what am I supposed to be doing, and how far along is it?". Weekly reports keep coming from Jira; this screen only makes the same tickets visible while I work.

Decided · Nov 23
  • Jira Cloud (*.atlassian.net)
  • All projects I'm assigned in, not only one
  • No story points: counts of tickets instead
  • Kanban board, same columns as on Jira: To Do · In Progress · In Review · Stage QA · Done (Backlog stays in the sidebar)
  • Read and write: move a ticket between columns, comment, assign, from Herdr
  • "Blocked" is a label on the ticket, not a status
  • The Jira API token lives in the Mac's Keychain
  • Herdr changes a ticket only when you click or move it, never on its own
  • First version skips the blocked label; add it later
1 · Data source

Four ways for a mod to read Jira

A mod can fetch URLs and exec programs, with no HTML and no built-in secret store. That rules out anything that needs a browser inside Herdr and makes "where does the token live?" the main question.

A · REST API v3 + API token · recommended

Direct fetch to /rest/api/3/search/jql with Basic auth (email:token)

  • No extra program: the mod calls Jira itself
  • You create one API token on id.atlassian.com (it works like a password for scripts) and save it once in the Mac's built-in password storage, Keychain. The screen reads it from there, so it is never written in a plain file.
  • Several sites are just several {site, email} entries, like Pulse's gh accounts
  • Agile API (/rest/agile/1.0/…) for boards and sprints, same token
  • Token is broad (acts as me); create a dedicated one, scoped if the site allows it
B · jira CLI via exec

ankitpokhrel/jira-cli: jira issue list --raw

  • It handles login, its own config and paging
  • Handy from a terminal too
  • An extra install, and its JSON follows the CLI's version
  • One config file per site; exec takes no env, so each call is sh -c 'JIRA_CONFIG_FILE=… jira …'
  • No sprint/board data beyond what the CLI exposes; still needs the same API token
C · Atlassian OAuth 2.0 (3LO)

Register an app, sign in through the browser, refresh tokens

  • Fine-grained scopes, read-only possible
  • accessible-resources lists every site at once
  • Needs a registered app, client secret and a redirect catcher (a local port or a custom URL scheme)
  • Rotating refresh tokens to store and renew: much more code for one user
D · Atlassian MCP / Rovo

Ask an agent with the Atlassian connector

  • Already connected in my Claude setup (it feeds the weekly report)
  • Not reachable from a mod: it lives in the agent, not in Herdr
  • Good for "write my report", not for a live page that refreshes

3 · Linking Jira ↔ PRs ↔ spaces

The issue key is the join

My spaces already show branch labels like HDE-314, and PR titles start with the key. The mod reads keys out of text with one pattern, \b[A-Z][A-Z0-9]+-\d+\b, limited to the project keys of my configured sites (so UTF-8 or SHA-256 never match).

HDE-314Jira ticket
→
feat/HDE-314-paginationgit branch
→
go-gql-api · HDE-314Herdr space (worktree)

Where keys are found

  • PRs: per gh account (same as Pulse), gh search prs --author=@me "HDE-314" matches titles and bodies; the head branch name is in the result (headRefName), so a PR titled "Pagination" on branch feat/HDE-314-… still links.
  • Spaces: spaces() gives each space's name and its terminals' folders; git branch --show-current per folder (the spaces sidebar already does this) gives the branch. A key in either links the space.
  • Title prefix: your tickets start with the repo, like [go-gql-api] - finality watermark. That prefix picks the repo, and so the space, even before a branch exists: "Start work" knows where to make the worktree.
  • Jira itself: your board already shows PR icons on tickets, so the GitHub for Jira app is installed, the ticket's development panel already knows its PRs. Its API is not public, so treat it as a bonus, not the source.

What the links make possible

  • Open in space: a linked space → space.select {id}. No space but a known repo → open the worktree mod with {branch: "feat/HDE-314-…"} to make one.
  • Start work: on a To Do ticket, suggest the branch name feat/HDE-315-finality-watermark and create the worktree space.
  • Mismatch hints: PR merged but ticket still In Review; ticket Done but PR still open.
  • Pulse gets the same lookup in reverse: a PR card shows its ticket's status.
  • One shared index (setShared("issueLinks", …)) so Pulse, Jira and the spaces sidebar don't each scan.
4 · Calls behind the page

One search per site

  • Tickets, every project: POST /rest/api/3/search/jql with jql: "assignee = currentUser() AND (statusCategory != Done OR resolved >= -14d)", fields: summary, status, issuetype, project, labels, updated.
  • Columns follow the ticket's status name (To Do, In Progress, In Review, Stage QA, Done); Backlog is a sidebar filter.
  • Blocked: labels = blocked (the label name is a setting).
  • Write back: move a ticket with GET then POST /rest/api/3/issue/{key}/transitions (the menu lists exactly the moves your workflow allows); comment with POST …/comment; assign with PUT …/assignee; add or remove the blocked label with PUT /rest/api/3/issue/{key}.
  • Saved filters are JQL strings in settings; also offer my Jira favourite filters (/rest/api/3/filter/favourite).
